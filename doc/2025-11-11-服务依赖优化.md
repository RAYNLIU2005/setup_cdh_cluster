## 问题背景

### 发现的问题

在实际部署过程中，发现 CM Server 启动时出现以下错误：

```
ERROR org.hibernate.engine.jdbc.spi.SqlExceptionHelper - Communications link failure
```

### 问题分析

通过日志分析发现：
- **MySQL** 启动时间：17:52:02
- **CM Server** 启动时间：17:18:45

**根本原因：** CM Server 在 MySQL 之前启动了 33 分钟，导致无法连接数据库。

### 影响范围

1. CM Server 无法正常初始化
2. Web 界面可能无法访问
3. 集群管理功能受限
4. 需要手动重启服务修复

---

## 解决方案

### 1. Ansible Playbook 优化

#### 文件：`ansible/component/setup_cloudera_manager_master.yml`

**添加的内容：**

```yaml
# 关键修复：确保 MySQL 就绪后再启动 CM Server
- name: 等待 MySQL 服务完全启动
  wait_for:
    host: localhost
    port: 3306
    state: started
    delay: 2
    timeout: 60
  ignore_errors: no

- name: 验证 MySQL 连接和 SCM 数据库
  shell: mysql -uroot -p"{{password.mysql}}" -e "USE scm; SELECT COUNT(*) FROM ROLES;" 2>&1
  register: mysql_scm_check
  retries: 5
  delay: 3
  until: mysql_scm_check.rc == 0
  ignore_errors: yes

- name: 启动 cloudera-scm-server 并设置开机自启动
  service:
    name: cloudera-scm-server
    state: started
    enabled: yes

- name: 等待 CM Server 启动（最多120秒）
  wait_for:
    port: 7180
    host: localhost
    delay: 5
    timeout: 120
  ignore_errors: yes

- name: 检查 CM Server 日志中的启动状态
  shell: journalctl -u cloudera-scm-server -n 50 --no-pager | grep -E "(Started Jetty|Communications link failure)" || echo "日志检查中..."
  register: cm_startup_log
  retries: 6
  delay: 10
  until: cm_startup_log.stdout is search("Started Jetty") or cm_startup_log.stdout is search("Communications link failure")
  ignore_errors: yes
```

**改进点：**
1. ✅ 添加 MySQL 端口就绪检查
2. ✅ 验证 MySQL 连接和 SCM 数据库
3. ✅ 添加 CM Server 启动等待
4. ✅ 监控启动日志，及时发现错误
5. ✅ 提供清晰的启动状态反馈

#### 文件：`ansible/component/setup_mysql_server.yml`

**添加的内容：**

```yaml
- name: 等待 MySQL 端口就绪（TCP 3306）
  wait_for:
    host: localhost
    port: 3306
    state: started
    delay: 2
    timeout: 30
  when: mysql_final_check.rc == 0

- name: 验证 MySQL 服务完全可用
  shell: mysql -uroot -p'{{password.mysql}}' -e "SELECT 1" 2>&1
  register: mysql_ready_check
  retries: 5
  delay: 2
  until: mysql_ready_check.rc == 0
  when: mysql_final_check.rc == 0
  ignore_errors: no
```

**改进点：**
1. ✅ 确保 MySQL 重启后完全就绪
2. ✅ 添加连接验证和重试机制
3. ✅ 提供明确的就绪状态提示

### 2. 新增运维工具

#### A. 健康检查脚本

**文件：** `scripts/health_check.sh`

**功能：**
- 检查所有服务运行状态
- 验证端口监听
- 测试 MySQL 连接
- 检查 CM Server 日志错误
- 验证 CM Web 可访问性
- 分析服务依赖关系

**使用：**
```bash
make health-check
```

**输出示例：**
```
========================================
  Master 节点服务检查 (node01)
========================================

--- MySQL 服务 ---
[INFO] ✓ MySQL Server 运行中
[INFO] ✓ MySQL 端口 3306 监听中
[INFO] ✓ MySQL 连接正常
[INFO] ✓ SCM 数据库正常

========================================
  健康检查总结
========================================

通过: 12 项
失败: 0 项
```

#### B. 深度诊断脚本

**文件：** `scripts/diagnose_dependencies.sh`

**功能：**
- 分析服务启动时间
- 检查启动顺序是否正确
- 识别依赖关系问题
- 分析错误日志
- 检查系统资源
- 提供修复建议

**使用：**
```bash
make diagnose
```

#### C. CM MySQL 连接修复

**文件：** `scripts/fix_cm_mysql_connection.sh`

**功能：**
- 检查 MySQL 状态和连接
- 验证 SCM 数据库
- 重启 CM Server
- 监控启动过程
- 自动检测和报告问题

**使用：**
```bash
make fix-cm-mysql
```

#### D. 服务重启管理

**文件：** `scripts/restart_services.sh`

**功能：**
- 按正确顺序停止服务
- 等待 MySQL 完全就绪
- 启动 CM Server 并验证
- 启动 CM Agent
- 提供详细状态反馈

**使用：**
```bash
make restart-services
```

## 技术亮点

### 1. 服务依赖检查

**问题：** 如何确保服务按正确顺序启动？

**方案：**
```yaml
- name: 等待 MySQL 服务完全启动
  wait_for:
    host: localhost
    port: 3306
    state: started
    delay: 2
    timeout: 60
```

**优势：**
- 阻塞式等待，确保依赖就绪
- 超时保护，避免无限等待
- 失败快速响应

### 2. 重试机制

**问题：** MySQL 启动后可能还需要时间初始化

**方案：**
```yaml
- name: 验证 MySQL 连接和 SCM 数据库
  shell: mysql -uroot -p"{{password.mysql}}" -e "USE scm; SELECT COUNT(*) FROM ROLES;"
  register: mysql_scm_check
  retries: 5
  delay: 3
  until: mysql_scm_check.rc == 0
```

**优势：**
- 多次重试，提高成功率
- 间隔等待，给服务初始化时间
- 条件判断，精确控制

### 3. 启动验证

**问题：** 如何知道服务真正启动成功？

**方案：**
```yaml
- name: 检查 CM Server 日志中的启动状态
  shell: journalctl -u cloudera-scm-server -n 50 --no-pager | grep -E "(Started Jetty|Communications link failure)"
  register: cm_startup_log
  retries: 6
  delay: 10
```

**优势：**
- 日志验证，确认真实状态
- 错误检测，及时发现问题
- 人性化反馈，提供修复建议

### 4. 自动化诊断

**设计理念：**
```
问题发现 → 健康检查 → 深度诊断 → 自动修复 → 验证结果
```

**实现：**
- `health-check`：快速发现问题
- `diagnose`：深入分析原因
- `fix-cm-mysql`：针对性修复
- 循环验证：确保问题解决

## 最佳实践总结

### 1. 部署阶段

✅ **DO:**
- 使用 `make full-deploy` 完整流程
- 部署后执行 `make health-check`
- 记录部署日志

❌ **DON'T:**
- 跳过环境检查
- 忽略错误提示
- 多次重试不分析原因

### 2. 运维阶段

✅ **DO:**
- 定期健康检查
- 使用工具脚本管理服务
- 问题诊断后再修复

❌ **DON'T:**
- 手动重启服务
- 忽视告警信息
- 盲目重启系统

### 3. 故障处理

✅ **DO:**
```bash
# 标准流程
make health-check      # 发现问题
make diagnose         # 诊断原因
make fix-cm-mysql     # 针对性修复
make health-check     # 验证结果
```

❌ **DON'T:**
- 不诊断直接修复
- 不验证就认为已解决
- 不记录问题和方案
