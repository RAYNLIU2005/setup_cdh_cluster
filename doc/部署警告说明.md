## 概述

部署过程中可能会看到一些**警告和失败信息**（显示为红色或黄色），但这些**不影响实际部署结果**。本文档详细说明这些警告的原因和是否需要处理。

---

## ✅ 可以安全忽略的警告

### 1. Python 3.6 弃用警告

#### 警告内容
```
CryptographyDeprecationWarning: Python 3.6 is no longer supported by the Python core team. 
Therefore, support for it is deprecated in cryptography. 
The next release of cryptography will remove support for Python 3.6.
```

#### 原因
- CentOS 7 默认提供 Python 3.6
- cryptography 库提示 Python 3.6 即将停止支持
- 但当前版本仍然可以正常工作

#### 是否需要处理
**❌ 不需要**

#### 影响
**✅ 无影响**，所有功能正常

#### 说明
这只是一个**未来警告**，提示将来可能需要升级 Python 版本。对当前部署和使用没有任何影响。

---

### 2. htop 安装失败

#### 警告内容
```
fatal: [node02]: FAILED! => {"changed": false, "msg": "No package matching 'htop' found available, installed or updated", "rc": 126, "results": ["No package matching 'htop' found available, installed or updated"]}
...ignoring
```

#### 原因
- htop 是一个**可选的**系统监控工具
- 某些 YUM 源可能没有 htop 包
- Ansible 脚本已设置为忽略此错误

#### 是否需要处理
**❌ 不需要**

#### 影响
**✅ 无影响**，htop 只是辅助工具，不影响 CDH 集群

#### 说明
htop 用于美化进程查看，使用系统自带的 `top` 命令可以达到同样效果。

---

### 3. Ansible 命令警告

#### 警告内容
```
[WARNING]: Consider using the yum module rather than running 'yum'. 
If you need to use command because yum is insufficient you can add 'warn: false' to this command task
```

#### 原因
- Ansible 建议使用专用的 `yum` 模块而不是 `shell` 或 `command` 模块
- 这只是一个**最佳实践建议**

#### 是否需要处理
**❌ 不需要**（不影响功能）

#### 影响
**✅ 无影响**，命令正常执行

#### 说明
这是 Ansible 的编码规范提示，不影响部署结果。

---

### 4. MySQL ROLES 表不存在

#### 警告内容
```
fatal: [node01]: FAILED! => {"attempts": 5, "changed": true, "cmd": "mysql -uroot -p\"Cloudera!20200801\" -e \"USE scm; SELECT COUNT(*) FROM ROLES;\" 2>&1", "msg": "non-zero return code", "rc": 1, "stdout": "ERROR 1146 (42S02) at line 1: Table 'scm.ROLES' doesn't exist"}
...ignoring
```

#### 原因
- 这是**正常现象**！
- `scm` 数据库在部署时创建
- 但表结构由 **CM Server 首次启动时**自动创建
- 检查时 CM Server 可能还未完全启动

#### 是否需要处理
**❌ 不需要**

#### 影响
**✅ 无影响**，CM Server 启动后会自动创建所有表

#### 说明
这是部署流程的正常阶段，CM Server 启动后会：
1. 连接到 scm 数据库
2. 自动创建所有需要的表结构
3. 初始化数据

等待 3-5 分钟后，表会自动创建完成。

---

### 5. CM Server 启动检查失败

#### 警告内容
```
FAILED - RETRYING: 检查 CM Server 日志中的启动状态 (6 retries left).
...
fatal: [node01]: FAILED! => {"attempts": 6, "changed": true, "stdout_lines": ["日志检查中..."]}
...ignoring

⚠ CM Server 正在启动中（可能需要几分钟）
```

#### 原因
- CM Server 启动需要 **3-5 分钟**
- Ansible 检查时 CM Server 可能还在启动中
- 日志中尚未出现 "Started Jetty server" 标记

#### 是否需要处理
**❌ 不需要**

#### 影响
**✅ 无影响**，等待启动完成即可

#### 说明
CM Server 启动过程：
1. 加载配置
2. 连接数据库
3. 初始化表结构
4. 启动 Web 服务（Jetty）
5. 完全就绪

**建议操作**：
```bash
# 实时查看启动日志
tail -f /var/log/cloudera-scm-server/cloudera-scm-server.log

# 等待看到这行，表示启动成功
INFO WebServerImpl:com.cloudera.server.cmf.WebServerImpl: Started Jetty server
```

### 6. MySQL 密码模块警告

#### 警告内容
```
[WARNING]: Module did not set no_log for update_password
```

#### 原因
- Ansible 的 MySQL 模块提示应该隐藏密码参数
- 这是 Ansible 模块的安全性建议

#### 是否需要处理
**❌ 不需要**

#### 影响
**✅ 无影响**，密码设置成功

#### 说明
这是 Ansible 的安全提示，不影响密码设置功能。

## 🔍 如何验证部署成功

虽然有警告信息，但可以通过以下方式验证部署是否成功：

### 方法 1：运行部署后检查脚本

```bash
make post-check
```

这个脚本会：
- ✅ 检查所有服务状态
- ✅ 检查端口监听
- ✅ 检查数据库
- ✅ 等待 CM Server 启动
- ✅ 显示访问信息

### 方法 2：手动检查关键服务

```bash
# 1. 检查服务状态
systemctl status mysqld
systemctl status httpd
systemctl status cloudera-scm-server
systemctl status cloudera-scm-agent

# 2. 检查端口
netstat -tlnp | grep -E "3306|80|7180|7182"

# 3. 检查日志
tail -f /var/log/cloudera-scm-server/cloudera-scm-server.log
```

### 方法 3：访问 Web 界面

等待 3-5 分钟后，访问：
```
http://node01:7180
```

如果能看到登录页面，说明部署成功！

## 📊 部署日志解读

### 成功的部署日志特征

```
PLAY RECAP ***************************************************
node01  : ok=106  changed=84   unreachable=0    failed=0    skipped=7    rescued=0    ignored=5
node02  : ok=43   changed=34   unreachable=0    failed=0    skipped=2    rescued=0    ignored=2
node03  : ok=43   changed=34   unreachable=0    failed=0    skipped=2    rescued=0    ignored=2

[INFO] 部署完成
```

**关键指标**：
- ✅ `failed=0` - 没有真正的失败任务
- ✅ `unreachable=0` - 所有节点可达
- ✅ `ignored=5` - 5个任务失败但被忽略（都是安全忽略）

### ignored 任务说明

`ignored=5` 表示有 5 个任务失败但被标记为可忽略：
1. htop 安装失败 (node02)
2. htop 安装失败 (node03)
3. createrepo 首次安装失败（之后从 EPEL 成功安装）
4. MySQL ROLES 表检查失败（正常现象）
5. CM Server 启动检查失败（需要等待）

这些都是**预期的、安全的失败**。

## 🎯 真正需要关注的错误

以下情况才需要处理：

### ❌ 真正的错误示例

```
# 服务启动失败
systemctl status cloudera-scm-server
● cloudera-scm-server.service - Cloudera SCM Server
   Loaded: loaded
   Active: failed (Result: exit-code)

# MySQL 连接失败
ERROR 2003 (HY000): Can't connect to MySQL server on 'localhost'

# 网络不通
fatal: [node02]: UNREACHABLE!
```

如果看到这些，请执行：
```bash
# 1. 查看详细日志
tail -100 /var/log/cloudera-scm-server/cloudera-scm-server.log

# 2. 运行诊断
make diagnose

# 3. 检查修复
make fix-cm-mysql
make restart-services
```

## 📝 总结

### 部署警告总结表

| 警告类型 | 是否需要处理 | 影响 | 说明 |
|---------|------------|------|------|
| Python 3.6 弃用 | ❌ 不需要 | ✅ 无影响 | 未来警告 |
| htop 安装失败 | ❌ 不需要 | ✅ 无影响 | 可选工具 |
| Ansible 命令警告 | ❌ 不需要 | ✅ 无影响 | 最佳实践建议 |
| MySQL ROLES 表不存在 | ❌ 不需要 | ✅ 无影响 | 正常现象 |
| CM Server 启动检查 | ❌ 不需要 | ✅ 无影响 | 需要等待 |
| MySQL 密码模块警告 | ❌ 不需要 | ✅ 无影响 | 安全提示 |

### 关键要点

1. **`ignored` 不等于失败**
   - Ansible 的 `ignored` 表示"失败但可以忽略"
   - 这是脚本有意设置的容错机制

2. **警告不影响使用**
   - 所有警告都是非关键性的
   - CDH 集群功能完全正常

3. **等待是必需的**
   - CM Server 启动需要 3-5 分钟
   - 数据库表由 CM Server 自动创建

4. **验证很简单**
   - 运行 `make post-check`
   - 或访问 http://node01:7180
